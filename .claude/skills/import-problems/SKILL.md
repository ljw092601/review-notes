# 사진 → 오답노트 가져오기 파일

사용자는 틀린 문제 사진을 `inbox/<날짜>/`에 넣고 "오답 정리해줘"라고만 말한다.
**되묻지 말고** 아래 순서대로 끝까지 처리한 뒤 짧게 보고한다. 사용자가 앱에서 할 일은
틀린 이유와 풀이를 적는 것뿐이다. 나머지(본문 텍스트, 답 형식, 유형, 태그, 정답)는 전부 여기서 채운다.

## 0. 역할 분담

| 항목 | 담당 |
|---|---|
| 문제 본문 텍스트 변환 (코드·표 포함, 마크다운) | Claude |
| 답 형식 판단 (`short` / `essay` / `choice`) | Claude |
| 문제 유형(`category`) + 태그 | Claude |
| 정답 (`correctAnswer`) | Claude. 사진에 정답·해설이 있으면 그대로, 없으면 직접 풀고 `answerConfidence`로 표시 |
| 내 답 (`myAnswer`) | 사진에 손글씨·체크 표시가 보이면 Claude, 아니면 빈 문자열 |
| 풀이 초안 (`explanation`) | Claude. 문제를 푸는 데 필요한 **핵심 개념**을 한두 문장 + 비교표·목록으로 정리한다. 풀이 과정·자주 틀리는 점은 쓰지 않는다. 사용자가 앱에서 다듬는다 |
| 틀린 이유 (`wrongReason`) | **사용자** (앱의 "입력 필요" 화면). 파일에 넣지 않는다 |

## 1. 절차

1. 처리할 폴더를 정한다. 사용자가 날짜를 말하지 않았으면 `inbox/` 아래에서 `done/` 밖에 사진이 남아 있는 가장 최근 날짜 폴더. 없으면 `inbox/` 바로 아래 사진들을 오늘 날짜 폴더로 옮긴 뒤 진행한다.
2. 사진을 **하나씩 Read로 열어 본다.** 한 장에 문제가 여러 개면 문제마다 한 건으로 나눈다. 한 문제가 두 장에 걸쳐 있으면 한 건에 `imageFiles` 두 개.
3. 문제마다 아래 2절 규칙으로 필드를 채워 `inbox/<날짜>/<날짜>.problems.json`에 쓴다(이미지 없이, 파일명만).
4. 빌드 스크립트로 최종 파일을 만든다. 이미지가 base64로 들어가고 사진은 `done/`으로 옮겨진다.
   ```
   node .claude/skills/import-problems/build.mjs inbox/<날짜>
   ```
   스크립트가 스키마 검증 오류를 내면 `.problems.json`을 고치고 다시 실행한다.
5. 보고: 처리한 사진 수, 만든 문제 수, 유형별 개수, `answerConfidence`가 `low`인 문제(이유 한 줄), `[판독불가]`가 들어간 문제. 마지막에 "앱 → 가져오기에서 `inbox/<날짜>/<날짜>.json`을 드롭하세요" 한 줄.

## 2. 필드 작성 규칙

`inbox/<날짜>/<날짜>.problems.json` 형식:

```json
{
  "version": 1,
  "problems": [
    {
      "certification": "정보처리기사",
      "category": "programming",
      "source": "2024년 2회 기출 7번",
      "answerType": "short",
      "question": "다음 C 코드의 출력 결과를 쓰시오.\n\n```c\nint a = 5, b = 3;\nprintf(\"%d\", a++ + ++b);\n```",
      "choices": null,
      "myAnswer": "8",
      "correctAnswer": "9",
      "answerConfidence": "high",
      "explanation": "**핵심 개념**: 증감 연산자는 `++`/`--`가 변수 앞에 오느냐 뒤에 오느냐에 따라 식에서 쓰는 값이 다르다.

| 형태 | 식에서 쓰는 값 | 변수는 |
|---|---|---|
| 후위 `a++` | 증가 전 값 | 식 평가 후 1 증가 |
| 전위 `++b` | 증가 후 값 | 먼저 1 증가 |

- 어느 쪽이든 문장이 끝나면 변수는 1 커져 있다. 차이는 그 식 안에서 쓰는 값뿐이다",
      "tags": ["증감연산자", "C"],
      "imageFiles": ["IMG_001.jpg"]
    }
  ]
}
```

- `certification`: 기본 `"정보처리기사"`. 사진에 다른 시험명이 명확히 보일 때만 바꾼다.
- `source`: 사진에 보이는 출처를 `"YYYY년 N회 기출 M번"`, `"<교재명> p.123 5번"` 식으로. 안 보이면 `""`. 같은 출처가 이미 앱에 있으면 중복으로 건너뛰므로 **지어내지 않는다.**
- `question`: 마크다운. 지문·보기·표·코드를 빠짐없이 옮긴다.
  - 코드는 언어 태그가 있는 펜스 코드 블록(```c, ```java, ```python, ```sql). 들여쓰기와 괄호를 원본 그대로.
  - 표는 GFM 표. 밑줄 빈칸은 `(  ①  )`처럼 번호를 붙여 둔다.
  - "답을 쓰시오" 같은 지시문도 포함. 문제 번호는 뺀다.
  - 읽을 수 없는 글자는 `[판독불가]`로 적고 추측하지 않는다. 손글씨 메모·채점 표시는 본문에 넣지 않는다.
- `answerType`: 보기에서 고르면 `choice`, 한두 단어·숫자·코드 출력값이면 `short`, 문장으로 설명해야 하면 `essay`.
- `choices`: `choice`일 때만 보기 문자열 배열(번호 없이 내용만, 순서 유지). 아니면 `null`.
- `myAnswer`: 사진에 사용자가 쓴 답이 보이면 그대로(틀린 답이어도). 없으면 `""`.
- `correctAnswer`:
  - 사진·해설에 정답이 있으면 그대로 → `answerConfidence: "high"`.
  - 없으면 직접 푼다. 계산·코드 추적 문제는 단계별로 검산한 뒤 답만 적는다. 확실하면 `"high"`, 용어 문제처럼 표현이 여러 가지일 수 있으면 `"medium"`, 자료 부족·판독불가·추론이 끼면 `"low"`.
  - 빈칸이 여럿이면 `"① ~, ② ~"` 형식. 서술형은 채점 기준이 될 핵심 문장 1~3개.
  - 풀이 과정은 넣지 않는다(풀이는 사용자 몫). 단, `low`일 때는 `"(확인 필요: ...)"`를 뒤에 짧게 붙여도 된다.
- `explanation`: **핵심 개념 정리**(마크다운). 이 문제를 푸는 데 필요한 개념을 "정리 노트"처럼 쓴다. 문제를 어떻게 푸는지(풀이 흐름)와 어디서 틀리기 쉬운지(자주 틀리는 점)는 **쓰지 않는다**. 그건 사용자가 틀린 이유에 적는다.
  - 시작은 `**핵심 개념**:` + 한두 문장. 이 문제가 무슨 개념을 묻는지, 그 개념의 한 줄 규칙.
  - 그 아래에 **비교표 또는 목록**으로 정리한다. 이것이 본체다.
    - 같이 외워야 하는 이웃 개념이 있으면 GFM 표로 비교(예: 정규형 단계, 네트워크 장비별 계층, 관계대수 vs 관계해석, 보기에 나온 패턴·용어 전부). 정답인 개념도 표 안에 한 행으로 들어간다.
    - 비교할 이웃이 없으면 핵심 규칙 2~4개를 `- ` 목록으로.
  - 코드·계산 문제는 실행 결과를 추적하지 말고, 그 코드가 쓰는 문법·규칙을 표나 목록으로(예: break 유무에 따른 switch 실행 범위, 증감식별 방문 인덱스).
  - 암기법이 있으면 마지막에 `**암기**:` 한 줄을 붙여도 된다(예: 도-부-이-결-다-조).
  - 전체 5~12줄. 교과서 설명을 길게 옮기지 않는다. `answerConfidence`가 `low`면 맨 끝에 "(확인 필요)"를 붙인다.
- `tags`: 2~4개. 세부 개념 이름(예: `서브넷`, `2NF`, `옵저버 패턴`, `SQL 인젝션`). 유형 이름을 다시 넣지 않는다. 기존 태그와 표기를 맞추고 싶으면 이전 날짜 폴더의 `.problems.json`을 참고한다.
- `imageFiles`: 이 문제가 나온 사진 파일명(폴더 기준 상대 경로). 빌드 스크립트가 base64로 바꾼다.

## 3. 문제 유형 분류표 (`category`)

앱의 기본 유형 id. **반드시 이 중 하나.** 애매하면 문제가 묻는 "답의 종류"로 정한다
(예: SQL 문법을 묻는 보안 문제 → `sql`, 보안 용어를 묻는 네트워크 문제 → `security`).

| id | 이름 | 넣는 것 |
|---|---|---|
| `programming` | 프로그래밍 | C / Java / Python 코드 실행 결과, 문법, 자료구조·알고리즘 |
| `sql` | SQL | DDL / DML / DCL, 조인, 서브쿼리, 뷰, 인덱스, SQL 실행 결과 |
| `database` | 데이터베이스 이론 | 정규화, 키, 무결성, 트랜잭션, 회복, 병행 제어, 관계대수 |
| `network` | 네트워크 | OSI 7계층, TCP/IP, 프로토콜, 라우팅, IP·서브넷, 네트워크 장비 |
| `security` | 보안 | 암호화 알고리즘, 공격 유형, 인증·접근통제, 보안 솔루션, 시큐어 코딩 |
| `os` | 운영체제 | 프로세스·스레드, 스케줄링, 메모리·페이지 교체, 파일 시스템, 교착상태, 유닉스 명령 |
| `design` | 소프트웨어 설계 | UML, 디자인 패턴, 아키텍처, 결합도·응집도, 모듈화, 객체지향 원칙 |
| `testing` | 테스트 | 화이트박스·블랙박스, 커버리지, 테스트 단계·종류, 테스트 오라클, 결함 관리 |
| `methodology` | 개발방법론·요구사항 | 폭포수·애자일, 비용산정, 요구사항 분석·검증, 프로젝트 관리 |
| `interface` | 인터페이스·통합 | EAI/ESB, 미들웨어, JSON/XML/AJAX, 인터페이스 보안·검증 |
| `release` | 형상관리·패키징 | 버전 관리 도구, 빌드·배포, 릴리즈 노트, DRM, 매뉴얼 |
| `terminology` | IT 신기술·용어 | 약어, 신기술 용어, 클라우드·빅데이터·AI 관련 개념 |
| `etc` | 기타 | 위에 안 들어가는 것 |

사용자가 앱에서 유형을 추가했을 수 있다. 앱 백업 파일(`review-notes-*.json`)이 리포에 있으면 그 `categories`도 사용 가능하다.

## 4. 하지 말 것

- 사용자에게 "이 문제 맞나요?"라고 되묻기. 불확실하면 `answerConfidence: "low"`로 표시하고 진행한다.
- 틀린 이유(`wrongReason`) 채우기. 그건 사용자만 안다. 스키마에 넣어도 빌드 스크립트가 제거한다.
- 풀이에 풀이 흐름·계산 추적·"자주 틀리는 점" 쓰기. 풀이 칸은 핵심 개념 정리만 담는다. 용어만 나열한 사전처럼 쓰지도, 교과서처럼 길게 쓰지도 않는다.
- base64를 직접 손으로 쓰기. 반드시 빌드 스크립트를 쓴다.
- 이미 `done/`에 있는 사진 다시 처리하기.

## 5. 산출물 위치

```
inbox/<날짜>/IMG_001.jpg          ← 입력 (처리 후 inbox/<날짜>/done/ 으로 이동)
inbox/<날짜>/<날짜>.problems.json ← Claude가 쓴 중간 파일 (이미지 파일명만)
inbox/<날짜>/<날짜>.json          ← 빌드 결과, 앱 가져오기에 드롭하는 파일
```

같은 날 두 번째로 처리하면 `<날짜>-2.json`처럼 번호를 붙인다(덮어쓰지 않는다).
